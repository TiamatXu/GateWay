# M3：虚拟句柄与异步任务托管

> 实施记录。结构设计见 `2026-08-26-m2-descriptor-layer-design.md` §4.3（句柄字段映射）
> 与 §4.4（提交与轮询显式关联）——描述文件长什么样在那里定完了，本文只记
> **运行期怎么跑**，以及实施中做出的、M2 没有覆盖到的决定。

## 1. 范围

本轮交付 M3 的前两块：

- 虚拟资源 ID 的签发与解析，`虚拟ID → (渠道, 上游ID, 归属, 预扣单号)` 映射
- 渠道亲和
- 异步任务状态机、轮询更新、终态结算
- 孤儿任务巡检
- `OnTerminal` 计费时点

**未做**：`RequestForm::{Multipart, Binary, JsonThenBinary}`、`ResponseForm::{Ndjson, Binary}`、
`BillingTiming::Metered`、`auth.credential: oauth2_client_credentials`、`auth.inject: sign`、
webhook 更新、统一任务 API、智能路由（策略需专项讨论，见路线图风险登记）。

火山引擎资产 API 依赖上面前两项，因此仍是延期状态；阿里云百炼的原生异步端点已接通。

## 2. 虚拟句柄的文本形态

`gwh_` + 32 位十六进制（UUID 的紧凑写法），如 `gwh_9f2c…`。

**为什么带前缀而不是裸 UUID**：句柄经常嵌在更长的串里——火山引擎的资产引用写作
`asset://<id>`，客户端拿到虚拟 ID 后会自己拼回这个格式再发回来。要在任意字符串里
把它认出来、换回去，就得有一个可扫描的定长记号。因此请求侧的替换是**扫描替换**
（串里出现几个换几个），响应侧的签发是**整值替换**（上游给的就是裸 ID）。

**否决的方案：允许客户端直接传上游 ID**。透传优先的直觉会想放行，但同一渠道的凭证
是所有租户共用的——放行等于「猜到别人的 `task_id` 就能查别人的任务」。消费位置上
取到的值不是虚拟句柄一律 400。

## 3. 归属与拒绝方式

句柄记录调用方的账户链，校验规则是**调用方的链里必须含有句柄的链首**（主计费主体）。

父账户的链不含子账户，因此父账户的 Key 查不到子账户的任务。跨层级查看是管理面的
功能，不该由数据平面顺手放开。

**「不存在」与「不属于你」都答 404**：用 403 区分开等于告诉对方这个 ID 是存在的。

## 4. 渠道亲和由实际解析到的句柄决定

M2 §4.3 说「`shape.handle` 回答这个端点要不要回原渠道」。实施中发现这句话不够：
火山引擎的 `video_generation_submit` 的 `shape.handle` 是 `Issues(task)`，但它在请求体里
引用了另一个端点签发的 `asset` 句柄——那份素材只在签发它的渠道上存在。

因此运行期的规则是：**只要请求里解析出了任何句柄，渠道就被钉死**，与 `shape.handle`
无关。`shape.handle` 仍是形态维度（推导 Hold 挂在谁身上），但不再是亲和的唯一来源。

多个句柄分属不同渠道时直接 400——没有哪个渠道能同时满足。

### 4.1 `handles.consume` 属于入站契约

亲和必须在**选渠道之前**算出来，而那时还没有 provider 绑定。所以「请求的哪些字段
携带句柄」不能只挂在各 provider 的绑定上，它是入站契约的一部分：同一入站路径上
各 provider 的 `handles.consume` 必须一致，加载期按 `contract_diff` 校验。

这也符合直觉——客户端不该因为流量落到哪个渠道而改写请求。

## 5. 签发是幂等的

`resource_handle` 上 `UNIQUE (channel_id, kind, upstream_id)`，重复签发返回既有句柄。

两处依赖这条：

1. 提交重试拿到相同的上游 ID 时，客户端必须看到同一个虚拟 ID，否则同一个资源会有
   两个句柄、两笔预扣。
2. **轮询响应回显上游 ID 的问题由它解决**：阿里云百炼的 `GET /api/v1/tasks/{id}` 会在
   响应体里回显 `output.task_id`。描述文件在轮询端点上也写一条 `handles.issue`，
   幂等签发就把它换回同一个虚拟 ID——0 行 Rust，客户端从头到尾只见得到自己手上那一个。

冲突行的归属与本次不一致时报错而非返回既有句柄：那意味着上游把同一个 ID 发给了
两个账户，宁可整个请求失败。

## 6. 状态解释挂在提交端点上

轮询端点可能是全 provider 共用的一个（阿里云百炼所有异步任务族共用
`GET /api/v1/tasks/{task_id}`），它自己说不出「这个任务算不算完成」。

因此 `async.state` 与 `async.terminal` 写在**提交**端点上，运行期的查法是：
消费到的 task 句柄 → 任务记录 → `submit_endpoint` → 该端点的 `async` 声明。
顺带校验被打到的轮询端点确实是它声明的那个，否则不按它的状态表解读。

**未知状态一律算运行中**：厂商随时可能加中间状态，把未知状态当失败会误结算。

## 7. 终态结算权靠条件更新抢占

```sql
UPDATE async_task SET phase = $2, ... WHERE handle_id = $1 AND phase = 0 RETURNING ...
```

只有把 `phase` 从 0 改走的那次调用拿到返回行，也只有它负责 capture。并发轮询、
客户端轮询与孤儿巡检撞车，都由这一条收口，不需要额外的锁。

## 8. 失败的任务不收费

终态是 `Failed` 时一律 `void`。理由：厂商对失败的生成任务普遍不收费，而我方也拿不到
权威用量——没有依据的扣费比漏收更糟。

真需要对失败收费时，应当由描述文件在失败终态上声明用量规则，届时再放开；
不在主干代码里写「某些厂商失败也要收」。

## 9. `on_submit` 只抬预扣，不做部分捕获

M2 §4.5 把 `on_submit` 记作「`extend` / `capture_partial` 调整」。实施时只做 `extend`：

提交响应给出的用量若已超过预扣额，把预扣抬上去；低于预扣额则什么都不做。
**只抬不降**——降低预扣不会少收钱（终态按实际用量捕获），却会让账户可用额度看起来
变多，反而放松了防超支。部分捕获留给 `Metered`（M3 后续），那里才有「已经消耗掉、
不会退回」的语义。

## 10. 预扣托管：`Hold::detach()` 与长 TTL

`OnTerminal` 的 Hold 必须活过提交请求。`Hold::detach()` 交出所有权并返回单号，
析构不再上报泄漏；单号落在 `resource_handle.hold_id` 上。

**托管不取消 TTL**：`GatewayConfig::task_hold_ttl`（默认 24 小时）仍写进 `hold.expires_at`，
任务永远不到终态时由 TTL 回收器撤销。这是防死冻结的兜底一道，不能因为「有人管着」
就取消——「有人管着」正是最容易出错的假设。

## 11. 非 token 维度的预扣上限来自 `usage.estimate`

`estimate_max` 原先只对 token 维度按配置上限估算，其余维度一律跳过。这让
`OnTerminal` 的任务类端点预扣恒为 0——等于没有预扣。

`PriceCtx` 因此新增 `estimate`：描述文件的 `usage.estimate` 在请求体上求出的用量向量。
token 维度仍走上限（输出量在请求时不可知），其余维度用估算值——视频时长、图片像素
这类维度的上限**就写在请求里**。

## 12. 缓冲响应是例外，不是常态

只有两种端点会把响应读全：声明了 `handles.issue` 的（要改写响应体），
以及消费 task 句柄的（要读状态字段）。其余一律维持零拷贝流式透传。

由此带来一条加载期校验：`handles.issue` 要求 `response: json`，且取值位置必须在体内。
流式与二进制响应无法原地改写，与其运行期静默不改写，不如加载期就说清楚。

## 13. 不计费端点不建 Hold

轮询、取消这类 `billing: not_billed` 的端点不再走预扣路径，因而也不要求配价格
（它们通常连 `model` 都没有）。但仍然留日志——没有金额动作不等于没有账可查。
`SettlementGuard` 的 Hold 因此变成 `Option`。

## 14. 一次异步任务两行日志

提交与终态结算是两次独立的事件，各写一行 `request_log`：提交那行 `quote.amount` 为空，
终态那行带金额。`request_log.handle_id` 把两者串起来。

终态那行的 `started_at` 取**提交时刻**，价格版本随之——改价不影响已提交的任务。

## 15. 孤儿巡检

`stale_tasks` 捞出「仍在运行中、且超过 `idle_for` 没人查询」的任务，逐个向上游查一次，
走与客户端轮询完全相同的 `task::advance`。两条路径共用一套终态语义，各写一遍必然漂移。

当前限制：只处理把任务 ID 放在**路径参数**里的轮询端点。放在请求体里的需要一份
请求模板，那是描述文件目前装不下的东西——遇到时再考虑加，不预先设计。

## 16. 已否决方案汇总

| 方案 | 否决理由 |
|---|---|
| 虚拟句柄用裸 UUID | 句柄常嵌在 `asset://<id>` 这类串里，没有定长记号就无法在任意字符串中识别 |
| 允许客户端直接传上游 ID | 同一渠道凭证为所有租户共用，放行等于猜到 ID 就能查别人的资源 |
| 「不属于你」答 403 | 等于告诉对方这个 ID 存在，与 404 一起构成枚举通道 |
| 亲和只看 `shape.handle` | 提交端点的 `shape.handle` 是 `Issues`，却可能在请求体里引用别的渠道签发的素材 |
| `handles.consume` 只挂在 provider 绑定上 | 亲和要在选渠道之前算出，那时还没有绑定；且客户端不该因渠道不同而改写请求 |
| 终态状态表放在轮询端点上 | 轮询端点可能全 provider 共用，它说不出某个任务算不算完成 |
| 未知状态当失败处理 | 厂商随时新增中间状态，会误结算 |
| 用锁保证终态只结算一次 | 条件更新 `WHERE phase = 0` 已经够，多一把锁多一处可失败的地方 |
| 托管后取消 Hold 的 TTL | 「有人管着」正是最容易出错的假设，TTL 回收器必须是无条件兜底 |
| `on_submit` 做部分捕获 | 提交时没有「已消耗、不退回」的语义，会与终态捕获重复计费 |
| 所有响应统一缓冲以便改写 | 透传优先是架构前提，缓冲只给必须缓冲的两类端点 |
